## 二、Critical 级问题（必须立即修复）

### CR-01：强制会话可被渲染进程直接解锁

**文件**：`src/main/enforcement/index.ts:296-299`

**问题**：`enforce:unlock` 和 `timer:stop` 两个 IPC 通道可直接结束强制会话，无任何权限校验。若渲染进程被 XSS 攻破，攻击者一行代码即可解除全部强制机制。

**修复**：强制会话中禁用直接解锁，仅允许通过紧急退出码触发。

```typescript
// 修复后
ipcMain.handle(IPC_CHANNELS.enforce.unlock, (): boolean => {
  if (active && isEnforcedLevel(active.level)) {
    throw new Error('强制会话中请使用紧急退出码解锁')
  }
  endEnforcement('manual')
  return true
})
```

---

### CR-02：强制会话中可直接修改恢复码绕过紧急退出

**文件**：`src/main/enforcement/index.ts:311-314`

**问题**：`emergency:setCode` 可在强制会话中直接设置新恢复码，攻击者两步即可绕过：设新密码 → 验证退出。

**修复**：强制会话中禁止修改恢复码，修改需验证旧密码。

```typescript
// 修复后
ipcMain.handle(
  IPC_CHANNELS.emergency.setCode,
  (_event, code: string, oldCode?: string): boolean => {
    if (active && isEnforcedLevel(active.level)) {
      throw new Error('强制会话中无法修改恢复码')
    }
    const hash = getSettings().recoveryCodeHash
    if (hash && oldCode && !bcrypt.compareSync(oldCode, hash)) {
      throw new Error('旧恢复码不正确')
    }
    emergency.setRecoveryCode(code ?? '')
    return true
  }
)
```

---

### CR-03：settings:set 可修改任意敏感设置

**文件**：`src/main/storage/settings.ts:64-66`

**问题**：`settings:set` 接受任意 `Record<string, unknown>`，可修改 `lockLevel`、`recoveryCodeHash`、`enforced` 等安全敏感设置，一行代码绕过全部强制。

**修复**：建立设置写入白名单，敏感设置禁止通过通用通道修改。

```typescript
const SENSITIVE_SETTINGS = new Set(['lockLevel', 'recoveryCodeHash', 'enforced', 'sessionMaxHours'])

export function setSettings(entries: Record<string, unknown>): AppSettings {
  const s = getStore()
  for (const [key, value] of Object.entries(entries)) {
    if (value === undefined) continue
    if (SENSITIVE_SETTINGS.has(key) || key.startsWith('enforced.')) {
      console.warn(`[settings] 拒绝写入敏感设置: ${key}`)
      continue
    }
    s.set(key, value as never)
  }
  // ...
}
```

### CR-04：preload 反向依赖 main/ipc，违反分层原则

**文件**：`src/preload/index.ts:3`、`src/preload/index.d.ts:1`

**问题**：preload 层从 `../main/ipc` 导入 IPC 通道常量和白名单函数，违反 Electron 分层依赖方向（preload 属于渲染进程沙箱，不应引用主进程代码）。未来 main/ipc 若引入 Node.js 特有依赖，preload 构建会失败或引入安全风险。

**修复**：将 `IPC_CHANNELS`、`IPC_EVENTS`、`isAllowedChannel`、`isAllowedEvent` 迁移到 `src/shared/ipc.ts`（纯类型 + 常量 + 纯函数），main 和 preload 都从 shared 层导入。

---

### CR-05：enforcement ↔ navigation 循环依赖

**文件**：`src/main/enforcement/index.ts:20` ↔ `src/main/navigation/index.ts:9`

**问题**：enforcement 导入 navigation 的 `closeVideo`，navigation 导入 enforcement 的 `assertExitSafety` 和 `EnforcementHandle`，形成双向依赖。模块初始化顺序敏感，重构风险高。

**修复**：

1. 将 `closeVideo` 调用改为通过回调注入（enforcement 不直接 import navigation）
2. 明确依赖方向：navigation → enforcement，enforcement 不反向调用 navigation

---

### CR-06：通用 invoke 方法绕过类型化 API 边界

**文件**：`src/preload/index.ts:78-83`

**问题**：preload 暴露了通用 `invoke(channel, ...args)` 方法，渲染层可调用任意白名单内的 IPC 通道，绕过了命名 API（如 `api.bili.search()`）的安全边界。这削弱了 preload 作为安全屏障的作用。

**修复**：

1. 评估移除通用 `invoke` 方法，仅保留命名 API
2. 或至少限制 `invoke` 仅用于开发模式

---

### CR-07：3 个 store 的 IPC 事件订阅永不取消

**文件**：

- `src/renderer/src/store/focusStore.ts:47-62`
- `src/renderer/src/store/sessionStore.ts:38-52`
- `src/renderer/src/store/englishStore.ts:64-105`

**问题**：三个 store 都使用模块级 `subscribed` 标志防止重复订阅，但订阅后永不取消。HMR 热更新时旧订阅不会清理（`subscribed` 重置后再次订阅），导致重复监听。高频事件（`timer:tick` 每秒一次、`ai:chunk` 流式问答）下泄漏影响放大。未来多窗口场景下为明确内存泄漏。

**修复**：统一使用 `globalThis` 标志防 HMR 重复，暴露 `destroy()` 方法清理订阅。

```typescript
// 修复后
const g = globalThis as unknown as { __focusEventsSubscribed?: boolean }
let unsubscribeFns: Array<() => void> = []

export const useFocusStore = create<FocusStore>((set, get) => ({
  init: async () => {
    if (!g.__focusEventsSubscribed) {
      g.__focusEventsSubscribed = true
      unsubscribeFns.push(
        window.api.on<TimerSnapshot>('timer:tick', (snap) => set({ snapshot: snap }))
        // ...
      )
    }
  },
  destroy: () => {
    unsubscribeFns.forEach((fn) => fn())
    unsubscribeFns = []
    g.__focusEventsSubscribed = false
  }
  // ...
}))
```

## 三、High 级问题（应优先修复）

### H-01：所有 IPC handler 缺少参数运行时验证

**文件**：遍及所有 IPC 注册文件

**问题**：所有 `ipcMain.handle` 参数仅依赖 TypeScript 类型断言，运行时类型被擦除。异常输入可能导致 TypeError 崩溃、数据库脏数据、潜在注入攻击。

**修复**：使用 zod 等 schema 验证库对关键 IPC 参数进行运行时校验。优先覆盖 `ai.englishAsk`、`enforce.applyDistractionPolicy`、`playRecords.importData` 等用户输入通道。

---

### H-02：bcrypt 同步哈希阻塞主进程

**文件**：`src/main/enforcement/emergencyExit.ts:30,53`

**问题**：`bcrypt.hashSync` / `compareSync` 阻塞主进程 100-200ms，导致窗口卡顿和 IPC 延迟。被恶意高频调用可造成拒绝服务。

**修复**：使用异步版本 `bcrypt.hash` 和 `bcrypt.compare`。

---

### H-03：缺少全局 unhandledRejection 保护

**文件**：`src/main/index.ts`

**问题**：大量异步操作中，"发射后不管"的 Promise（如 `void saveCacheIndex()`）如果 reject，将成为 unhandledRejection。Node.js 新版本中会导致进程退出。

**修复**：在 `index.ts` 中注册全局 `unhandledRejection` 和 `uncaughtException` 处理器。

---

### H-04：守护进程无认证机制，PID 文件可被伪造

**文件**：`src/main/guardian/guardian.ts:34-44`

**问题**：守护进程通过 PID 文件检测主进程存活，无认证机制。本地恶意程序可伪造 PID 文件干扰守护行为。`relaunchCmd` 参数若可控可能拉起任意程序。

**修复**：增加共享密钥认证；限制 relaunchCmd 只能是主进程自身路径。

---

### H-05：bili-image 自定义协议 bypassCSP 权限过大

**文件**：`src/main/index.ts:31-40`

**问题**：`bili-image` 协议设置了 `bypassCSP: true`，可绕过页面内容安全策略。图片资源通常不需要绕过 CSP。

**修复**：移除 `bypassCSP: true`。

---

### H-06：全量解构 store 导致每秒全量重渲染

**文件**：

- `src/renderer/src/pages/FocusPage.tsx:25-38`
- `src/renderer/src/components/SessionTimerBar.tsx:53-54`

**问题**：FocusPage 和 SessionTimerBar 全量解构 `useFocusStore()` / `useSessionStore()`，每秒 tick 触发完整重渲染。番茄钟高频更新场景下性能浪费明显。

**修复**：使用 zustand selector 语法逐一订阅所需字段，或使用 `shallow` 比较。

---

### H-07：OverlayApp 与 LearningAssistantDrawer 大量重复逻辑

**文件**：`overlay/OverlayApp.tsx` 与 `components/LearningAssistantDrawer.tsx`

**问题**：两个组件约 200+ 行重复代码：笔记逻辑（防抖保存、CRUD、重点标记）、AI 流式问答（requestId、chunk 订阅、历史消息、错误处理）、AI 回答记入笔记。维护成本翻倍，bug 容易只修一边。

**修复**：抽离 `useNotes()` hook 封装笔记状态 + 自动保存 + CRUD；抽离 `useBiliAiChat()` hook 封装流式问答逻辑。

---

### H-08：NoiseEngine.emit() 拖拽时高频触发全量刷新

**文件**：`src/renderer/src/audio/engine.ts:67-69`

**问题**：`NoiseEngine` 是全局单例，每次 `setMasterVolume` 等操作都调用 `emit()` 通知所有订阅者。Slider 拖拽时每帧触发，所有订阅组件全部重渲染，性能损耗明显。

**修复**：对 `emit()` 做 `requestAnimationFrame` 节流；或 UI 层使用细粒度选择。

---

### H-09：OverlayApp 组件过大（639 行），职责过多

**文件**：`src/renderer/src/overlay/OverlayApp.tsx`

**问题**：单文件 639 行，混合了窗口管理、AI 对话、笔记、进度心跳、视频操作等 7+ 种职责，15 种 action type 的 useReducer。违反单一职责原则。

**修复**：AI 对话 → `useBiliAiChat()` hook；笔记 → `useNotes()` hook；进度心跳 → `useSessionTick()` hook；头部/页签 → 抽离子组件。

---

### H-10：SettingsPage 组件过大（642 行），表单逻辑耦合

**文件**：`src/renderer/src/pages/SettingsPage.tsx`

**问题**：单文件 642 行，包含 8 个设置分组的全部表单逻辑，每个配置项的保存模式高度重复。

**修复**：按设置分组拆分为子组件（`LockSettings` / `PomodoroSettings` / `AiSettings` / `BackupSettings` 等）；抽离通用 `useSetting<T>(key)` hook。

---

### H-11：英语模式与 视频学习模式 AI 对话逻辑重复

**文件**：`pages/EnglishModePage.tsx` 与 `overlay/OverlayApp.tsx` / `components/LearningAssistantDrawer.tsx`

**问题**：英语模式和 视频学习模式的 AI 对话各自维护一套消息状态和流式处理逻辑，数据流不统一。`MessageItem` 组件重复定义。

**修复**：统一为通用 `useAiChatStore`，支持不同场景（英语 / 视频学习）；`MessageItem` 移到 `components/` 复用。

---

### H-12：缺少 ESLint / Prettier 代码规范工具链

**问题**：项目无代码规范工具，长期多人协作会导致代码风格不一致、潜在 bug 无法静态捕获。

**修复**：引入 ESLint + @typescript-eslint + Prettier + eslint-plugin-react + eslint-plugin-import。

### H-13：缺少 CI/CD 配置

**问题**：没有自动化的类型检查、测试、构建流水线。代码质量完全依赖本地执行。

**修复**：配置 GitHub Actions，至少包含 typecheck、test、build；配置 PR 检查规则。

### H-14：核心业务模块测试覆盖为零

**问题**：enforcement、navigation、TimerService、session、白噪音引擎等核心逻辑完全没有单元测试，恰恰是业务复杂度最高、最容易出 bug 的地方。

**修复**：优先补充 TimerService、enforcement 状态机、navigation guard 四层判定的单元测试。

### H-15：package.json 运行时依赖放错位置

**问题**：`antd`、`react`、`zustand`、`react-markdown` 等运行时依赖放在 `devDependencies` 中，语义错误，可能影响依赖审计。

**修复**：将运行时依赖移动到 `dependencies`。

### H-16：AiReply 接口命名空间冲突

**文件**：`src/shared/bili.ts:192-197` 与 `src/shared/ai.ts:62-65`

**问题**：两个模块都定义了 `AiReply` 接口但结构不同，preload 中需用 `as` 重命名区分。

## 七、长期代码质量提升策略

### 7.1 建立代码质量门禁

1. **Pre-commit 钩子**：lint-staged 运行 ESLint + Prettier
2. **Pre-push 钩子**：运行 typecheck + 单元测试
3. **CI 流水线**：PR 必须通过 typecheck + test + build 才能合并
4. **代码审查规范**：建立 CR checklist，关键模块需双人审查

### 7.2 制定编码规范

1. **TypeScript 规范**：严格模式、零 any、优先类型推导
2. **React 规范**：组件职责单一（< 300 行）、hooks 依赖完整、避免全量 store 解构
3. **Electron 安全规范**：IPC 参数校验、最小权限原则、敏感设置写入保护
4. **命名规范**：文件/变量/函数命名统一，中文注释说明"为什么"而非"是什么"

### 7.3 测试策略

1. **测试金字塔**：单元测试为主（70%）、集成测试为辅（20%）、E2E 测试少量（10%）
2. **覆盖率目标**：核心模块 > 80%，整体 > 60%
3. **回归测试**：每个 bug fix 必须伴随回归测试
4. **测试类型**：纯函数测试 → 状态机测试 → 组件测试 → IPC 集成测试

### 7.4 架构守护

1. **依赖约束**：使用 eslint-plugin-import 限制模块间依赖方向
2. **定期审查**：每季度进行一次架构健康度检查
3. **ADR 制度**：重要技术决策必须记录为 ADR
4. **技术债务管理**：建立技术债务清单，按优先级逐步偿还

### 7.5 持续改进

1. **代码度量**：定期统计代码行数、圈复杂度、重复率
2. **故障复盘**：每次线上问题都进行根因分析，沉淀为规则/测试
3. **知识分享**：定期 code review 分享会，提升团队整体水平
